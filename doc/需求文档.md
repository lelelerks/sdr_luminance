# SDR Luminance — Win11 HDR 模式下 SDR 内容亮度快捷调节工具

> 需求文档 · v1.0 · 2026-08-03

---

## 1. 项目背景与目标

### 1.1 背景

Windows 11 开启 HDR 后，SDR 内容（桌面、浏览器、聊天软件等绝大多数应用）的显示亮度并不由显示器物理亮度决定，而是由系统的「SDR 内容亮度」参数控制。该参数位于：

> 设置 → 系统 → 屏幕 → HDR → SDR 内容亮度

存在两个实际痛点：

1. **入口过深**：需要四层菜单才能到达，且系统未提供任何快捷键。
2. **使用场景冲突**：最需要调节的时刻恰恰是全屏游戏或全屏观影时——而此时切出全屏去翻设置菜单，代价极高，甚至可能导致游戏崩溃或掉出全屏状态。

在 HDR 模式下，SDR 亮度过高会让桌面刺眼、过低会让字迹发灰，且不同内容（游戏 HUD、字幕、网页）的合适取值并不相同，因此这是一个**需要频繁调节**的参数。

### 1.2 目标

开发一个常驻系统托盘的轻量级原生工具，提供：

- 一个可拖动的滑杆窗口，实时改变系统 SDR 内容亮度
- 全局快捷键，在窗口最小化时也能调节亮度、唤起窗口
- 窗口置顶能力，使其可以浮于全屏程序之上，实现「一边看游戏画面一边调亮度」

**核心约束**：本工具需长期常驻后台并在游戏运行时使用，因此系统资源开销必须压到最低，不得与前台程序争抢任何资源。

## 2. 功能需求

### FR-1 可视化亮度调节窗口

**描述**
提供一个图形窗口，包含一条水平滑杆。拖动滑杆时，系统的 SDR 内容亮度实时同步变化。

**细则**
- 滑杆取值范围 `0–100`，与 Windows 设置页中的滑杆刻度**一一对应**
- 滑杆旁实时显示当前数值
- 程序启动时读取系统当前值填入滑杆，**不主动修改系统亮度**
- 拖动过程中亮度实时跟随（非松手后才生效）

**验收标准**
- [ ] 拖动滑杆时屏幕亮度即时变化，无明显延迟
- [ ] 拖动结束后打开 Windows 设置页，其滑杆位置与本程序数值一致
- [ ] 关闭本程序后，亮度设置依然保持（已持久化到系统）
- [ ] 程序启动瞬间屏幕亮度不发生任何跳变

---

### FR-2 全局快捷键

**描述**
支持在程序最小化（隐藏至托盘）状态下，通过全局快捷键调节亮度与唤起窗口。

**细则**
- 三个可绑定键位：
  | 功能 | 默认组合键 |
  |---|---|
  | 调亮一档 | `Ctrl + Alt + PageUp` |
  | 调暗一档 | `Ctrl + Alt + PageDown` |
  | 唤起窗口 | `Ctrl + Alt + B` |
- 三个键位**均可在设置界面内自定义**，采用「按下即录制」的交互方式
- 「唤起窗口」为**纯开关**：窗口可见则隐藏，隐藏则显示。不区分窗口是用户打开的还是
  快捷键自动弹出的（FR-7）—— 单一语义最易预期
- 按一次调整一档；**长按时由系统键盘重复机制自动连发**，实现连续调节
- 单档步进值**可自定义**（范围 `1–50`，默认 `5`）
- 调整结果 clamp 到 `[0, 100]`，到达边界后不再变化
- 快捷键在任意前台程序（含全屏游戏）下均可响应
- 若用户设置的组合键已被其他程序占用，需给出明确提示，并**保留原有配置不丢失**

**验收标准**
- [ ] 程序隐藏至托盘后，按快捷键屏幕亮度发生变化
- [ ] 长按快捷键可连续调节，松开即停
- [ ] 唤起快捷键能将隐藏的窗口显示出来；窗口已显示时再按一次将其隐藏
- [ ] 在设置页修改任一快捷键后**立即生效**，无需重启程序
- [ ] 故意绑定一个已被占用的组合键（如 `Ctrl+Alt+Del` 类系统保留键），程序给出提示且原配置未被破坏
- [ ] 修改步进值后，快捷键调节的幅度随之改变

---

### FR-3 非 HDR 模式下的不可用提示

**描述**
「SDR 内容亮度」仅在显示器开启 HDR 时有意义。当系统未处于 HDR 模式时，程序须明确提示功能不可用，而非静默失败或误改设置。

**细则**
- 检测目标为**系统主显示器**的 HDR 激活状态
- 非 HDR 时：
  - 滑杆置为禁用（灰显），不可拖动
  - 状态栏文字提示「当前显示器未开启 HDR，此功能不可用」
  - 托盘图标切换为灰色版本，以便一眼分辨
  - 快捷键按下时不执行任何亮度写入操作
- HDR 状态发生变化时，界面须**自动刷新**，无需重启程序或手动操作
- 状态检测必须为**事件驱动**，禁止使用定时轮询

> **实测行为记录（非缺陷）**：关闭 HDR 后，系统会把 `SDRWhiteLevel` 报为基准值 1000
> （即 80 nits，SDR 参考白电平），因此界面上的数值会显示为 **0** 而非保留关闭前的值。
> 这是系统的真实语义——HDR 关闭时「SDR 内容亮度」这一参数本就不存在。
> 重新开启 HDR 后，系统会按显示器恢复原先的设定值并同步回界面，用户设置不会丢失。
> 此行为经用户实测确认并接受，不作修改。

**验收标准**
- [ ] 在 HDR 关闭状态下启动程序，界面呈灰显并显示提示文字
- [x] 程序运行中关闭系统 HDR，界面自动置灰（实测：`Win+Alt+B` 切换后立即生效）
- [x] 重新开启 HDR，界面自动恢复可用并同步当前亮度值（实测通过）
- [ ] 非 HDR 状态下按快捷键，系统设置无任何变化
- [ ] 上述过程中，程序 CPU 占用始终为 0%（证明无轮询）

> **关键结论**：上述实测证明 Windows 11 切换 HDR 时会发送 `WM_DISPLAYCHANGE`，
> 界面无需任何轮询即可自动响应。这是「零轮询」设计（FR-4）能够成立的前提。

### FR-5 开机自启动开关

**描述**
在界面中提供开关，控制程序是否随 Windows 启动而自动运行。

**细则**
- 采用注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 机制，**不需要管理员权限**
- 写入值为 `"<exe 绝对路径>" --tray`；`--tray` 参数使程序启动后直接隐藏至托盘，不弹出窗口
- 开关状态**以注册表为唯一数据源**，每次读取都实时查询，不缓存到配置文件，避免两处状态不一致
- 设置对话框与托盘右键菜单中的该开关须共享同一状态
- 程序文件被移动后，启动时自动修正注册表中记录的路径（`autostart::RefreshPath`），
  免去用户手动重新开关一次

**验收标准**
- [ ] 勾选开关 → 重启电脑 → 程序静默常驻托盘，不弹窗，快捷键可用
- [ ] 取消勾选 → 重启电脑 → 程序不再自动启动
- [ ] 在托盘菜单勾选后打开设置对话框，该处勾选状态同步为已勾选

### FR-6 全屏程序之上的窗口置顶

**描述**
在其他程序全屏运行时，本程序的调节窗口须浮于其上，使用户能一边观察全屏画面（如游戏）一边拖动滑杆调节亮度。

**细则**
- 窗口始终保持置顶（topmost），并在被其他程序抢占层级后**自动恢复置顶**
- 窗口设为**不抢焦点**：点击滑杆进行拖动时，前台的全屏程序**不失去焦点、不掉出全屏、不最小化**——这是本需求能实际用起来的关键
- 窗口不出现在任务栏与 `Alt+Tab` 列表中（配合托盘常驻，避免干扰）
- 窗口位置可拖动并被记忆，下次启动还原到上次位置

**验收标准**
- [ ] 启动一款无边框窗口化全屏游戏，本程序窗口浮于游戏画面之上且清晰可见
- [ ] 拖动滑杆过程中，游戏保持前台焦点、不掉出全屏、不最小化
- [ ] 调节时游戏画面亮度实时变化，可直接目视比对效果
- [ ] 关闭再打开程序，窗口回到上次所在位置

**⚠️ 已知限制**：见第 8 章。独占全屏（Exclusive Fullscreen）模式下本窗口不可见。

### FR-7 快捷键调节时自动弹出窗口

**描述**
窗口收在托盘时用快捷键调节亮度，用户看不到当前数值，只能靠画面变化盲调（托盘 tooltip 带数值，但需鼠标悬停，全屏游戏中不可用）。
故在此情形下自动把窗口弹出来显示数值，停手后自动收回。

**细则**
- **仅在窗口处于隐藏态时触发**。窗口已可见时快捷键行为完全不变，不做任何额外处理
- 弹出沿用 FR-6 的 `SW_SHOWNOACTIVATE` + `WS_EX_NOACTIVATE` 路径，**不抢前台程序焦点**
- 停留时长自**最后一次**按键起算，长按连发期间持续重置，停手后才开始计时
- 亮度已到边界（`0` / `100`）时继续按键**同样刷新计时**：计时以「按了键」为准而非「值变了」，
  否则用户在最大亮度下按住调亮键，窗口会在他手底下消失
- 停留时长**可自定义**（范围 `500–10000` 毫秒，默认 `1500`）
- 到点后 `ShowWindow(SW_HIDE)` 收回托盘，与关闭按钮语义一致（本程序无最小化态）
- **用户在倒计时期间主动介入则转为常驻**：**点击窗口任意位置**、点托盘图标、拖滑杆、右键托盘、
  打开设置页之后，窗口不再自动消失，只能由用户自己关闭。
  「点击窗口任意位置」是最直接的接管方式，由窗口过程顶部的鼠标按下前置拦截统一兜住
  （`WM_*BUTTONDOWN` / `WM_NC*BUTTONDOWN` 覆盖客户区与标题栏，`WM_PARENTNOTIFY` 覆盖子控件）。
  **不可改用 `WM_MOUSEACTIVATE`**：它只在窗口非活动时发送，而托盘菜单的 `SetForegroundWindow`
  与设置窗口销毁后的激活交还都会让主窗口变为活动窗口，此后点击收不到该消息 ——
  症状是「偶尔点空白处/标题栏无法转常驻」，且依赖历史操作而极难复现
- **按「唤起窗口」键不属于介入，而是直接隐藏**（该键为纯开关，见 FR-2）
- 未开启 HDR 时不弹窗 —— 此时快捷键本就不执行任何写入（FR-3），弹一个全灰的窗口无意义

**验收标准**
- [ ] 窗口隐藏时按调节快捷键，窗口弹出显示数值，约 1.5 秒后自动消失
- [ ] 长按连发期间窗口保持可见，松手后才开始计时
- [ ] 窗口已打开时按快捷键，窗口**不会**自动消失
- [ ] 自动弹出后立刻点击窗口（空白处 / 标题栏 / 滑杆 / 按钮），窗口转为常驻不再自动消失
- [ ] 自动弹出后点托盘图标 / 右键托盘 / 开设置页，同样转为常驻
- [ ] 自动弹出后按唤起键，窗口**隐藏**（该键为开关，不是介入）
- [ ] 全屏游戏中触发弹窗，游戏不失焦、不掉出全屏
- [ ] 未开启 HDR 时按调节快捷键，窗口不弹出
- [ ] 修改停留时长后立即生效，重启程序后配置仍在

## 3. 技术方案

### 3.1 SDR 白电平的读取与写入

Windows 设置页中的「SDR 内容亮度」滑杆，底层对应的是显示器的 **SDR 白电平（SDR White Level）** 参数。

**写入**通过 `DisplayConfigSetDeviceInfo` 的一个**非公开** info type 完成：

```cpp
constexpr UINT32 DEVICE_INFO_SET_SDR_WHITE_LEVEL = 0xFFFFFFEE;   // 非公开

struct DISPLAYCONFIG_SET_SDR_WHITE_LEVEL {
    DISPLAYCONFIG_DEVICE_INFO_HEADER header;   // 20 字节
    UINT32 SDRWhiteLevel;
    BYTE   finalValue;
};
```

**读取**使用公开 API：`DISPLAYCONFIG_DEVICE_INFO_GET_SDR_WHITE_LEVEL`（值为 `11`），返回 `DISPLAYCONFIG_SDR_WHITE_LEVEL` 结构。

#### 换算关系

`SDRWhiteLevel` 的物理含义是「以 80 nits 为单位的千分比」，即 `nits = SDRWhiteLevel × 80 / 1000`。系统滑杆的 `0–100` 刻度对应 `80–480 nits`，每刻度 4 nits：

```
nits          = 80 + slider × 4              // slider ∈ [0,100] → 80..480 nits
SDRWhiteLevel = nits × 1000 / 80
              = 1000 + slider × 50           // → 1000..6000
slider        = (SDRWhiteLevel − 1000) / 50
```

即滑杆刻度与 `SDRWhiteLevel` 呈简单线性关系，每刻度 50。

#### finalValue 标志位

`finalValue` 是**持久化标志**，这是本方案在性能上的关键设计：

| 取值 | 行为 | 使用时机 |
|---|---|---|
| `0` | 亮度立即生效，但**不写入系统持久化配置** | 滑杆拖动过程中 |
| `1` | 亮度生效并**持久化**到系统配置 | 滑杆松手时、快捷键单次调节时 |

利用该标志，拖动滑杆的连续调节过程完全不触发系统配置写入，消除了高频磁盘 I/O。

### 3.2 主显示器的定位

写入 API 需要目标显示器的 `adapterId` + `targetId`，获取流程：

1. `MonitorFromPoint({0,0}, MONITOR_DEFAULTTOPRIMARY)` + `GetMonitorInfoW` → 取得主显示器的 GDI 设备名（形如 `\\.\DISPLAY1`）
2. `GetDisplayConfigBufferSizes(QDC_ONLY_ACTIVE_PATHS, ...)` + `QueryDisplayConfig` → 取得全部活动显示路径
3. 逐条 path 调用 `DISPLAYCONFIG_DEVICE_INFO_GET_SOURCE_NAME`，将返回的 `viewGdiDeviceName` 与第 1 步结果比对
4. 命中后取该 path 的 `targetInfo.adapterId` 与 `targetInfo.id`

> **注意**：`adapterId` / `id` 必须取自 `targetInfo` 而非 `sourceInfo`。

查询结果予以**缓存**，仅在收到 `WM_DISPLAYCHANGE` 消息时失效并重新查询——避免每次调节都执行一次完整的显示配置枚举。

### 3.3 HDR 状态检测

- **首选**：`DISPLAYCONFIG_DEVICE_INFO_GET_ADVANCED_COLOR_INFO_2`（值为 `15`），判断 `activeColorMode == DISPLAYCONFIG_ADVANCED_COLOR_MODE_HDR`
- **回退**：上述 type 调用失败时（旧版 Windows），改用 `GET_ADVANCED_COLOR_INFO`（值为 `9`）读取 `advancedColorEnabled` 位

> ⚠️ 注意 `GET_ADVANCED_COLOR_INFO_2` 的枚举值是 **15** 而非 14——`14` 是 `DISPLAYCONFIG_DEVICE_INFO_SET_RESERVED1`，误用会调到完全不同的接口。
>
> 该结构体在 `wingdi.h` 中受 `#if (NTDDI_VERSION >= NTDDI_WIN11_GA)` 保护，源文件须在 `#include <windows.h>` 之前定义
> `NTDDI_VERSION` 为 `0x0A00000F`（`NTDDI_WIN11_GA`），否则结构体不可见。
>
> 开发目标机为 Windows 11 24H2（10.0.26100），Windows SDK 同为 10.0.26100，两种 type 均实测可用。

**状态变化的感知完全由 `WM_DISPLAYCHANGE` 窗口消息驱动**——HDR 开关切换会触发该消息。程序在收到消息时清空缓存、重查状态、刷新界面。全程无定时器、无轮询，这是 FR-3 与 FR-4 能同时成立的基础。

### 3.4 置顶与焦点策略

窗口扩展样式组合：

| 样式 | 作用 |
|---|---|
| `WS_EX_TOPMOST` | 窗口置于普通窗口之上 |
| `WS_EX_TOOLWINDOW` | 不出现在任务栏与 `Alt+Tab` 列表 |
| `WS_EX_NOACTIVATE` | **点击窗口不夺取前台焦点** —— FR-6 的关键 |

此外在 `WM_WINDOWPOSCHANGING` 消息中强制将 `hwndInsertAfter` 置为 `HWND_TOPMOST`，防止某些全屏程序将本窗口压至下层。该做法为纯消息响应，零额外开销。

**例外**：设置对话框**不使用** `WS_EX_NOACTIVATE`。因为快捷键录制需要接收键盘输入，而 `NOACTIVATE` 窗口无法获得键盘焦点。设置操作不存在「一边玩游戏一边配置」的场景，故此例外无副作用。

**设置窗口的定位**：先居中于主窗口，再整体推回目标显示器的工作区（`rcWork`，以避开任务栏）。
主窗口远小于设置窗口，被拖到屏幕边角时居中结果必然越界。
注意不能用 `MonitorFromRect` + `MONITOR_DEFAULTTONULL` 判断越界 —— 它只在矩形与所有显示器
毫无交集时才返回 null，「部分越界」完全挡不住。须改用 `MONITOR_DEFAULTTONEAREST` 取显示器后
逐边 clamp，且先压右/下再压左/上，使窗口大于工作区时仍保住标题栏与按钮。

### 3.5 配置存储

- 路径：`%LOCALAPPDATA%\SdrLuminance\config.ini`
  - 选择该位置而非程序同目录，是为避免程序被放入 `Program Files` 时无写入权限
- 读写使用 `GetPrivateProfileIntW` / `GetPrivateProfileStringW` / `WritePrivateProfileStringW`，零第三方依赖
- 存储项：三组快捷键、步进值、弹窗停留时长、窗口位置
- **自启动状态不入 ini**，以注册表为唯一数据源（见 FR-5）

| 决策项 | 结论 | 理由 |
|---|---|---|
| **技术栈** | C++17 + 纯 Win32 API，无 UI 框架，静态链接 CRT | 唯一能同时满足「单文件无依赖」「内存 < 5MB」「空闲 CPU 0%」三项硬指标的方案。备选的 C# NativeAOT 内存约为其 5 倍（15–25 MB），WPF 更高达 40–70 MB 且带 GPU 合成开销，与 FR-4 冲突 |
| **多显示器** | 仅作用于系统主显示器 | 实际使用场景为单 HDR 主屏。支持多屏需引入显示器选择 UI、独立配置存储与逐屏状态跟踪，复杂度显著上升而收益有限。遵循 YAGNI |
| **置顶策略** | 标准 `TOPMOST` + `NOACTIVATE`，接受独占全屏限制 | 第三方 overlay 注入方案（Hook D3D 交换链）虽能覆盖独占全屏，但极易被游戏反作弊系统判定为外挂导致封号，且开销与复杂度剧增。当今绝大多数游戏默认即为无边框窗口化模式，标准方案已覆盖主要场景 |
| **快捷键行为** | 按一次调一档，长按由系统键盘重复自动连发 | `RegisterHotKey` 不加 `MOD_NOREPEAT` 时，Windows 会依系统键盘重复率自然连发 `WM_HOTKEY`，零成本实现长按连续调节。备选的「组合键 + 鼠标滚轮」方案需常驻全局鼠标钩子（`WH_MOUSE_LL`），该钩子会拦截系统全部鼠标消息，与 FR-4 冲突 |
| **快捷键配置** | UI 内按键录制，三个键位全部可自定义 | 全局快捷键与其他软件冲突的概率很高，写死组合键会导致冲突时完全无法使用。录制式交互比手改配置文件的体验好得多 |
| **步进值** | 设置页可自定义，范围 1–50，默认 5 | 不同用户对调节粒度的偏好差异大：观影时希望大步快调，办公时希望小步微调。默认 5（对应 20 nits）为折中值 |
| **启动时的亮度** | 只读取系统当前值同步到滑杆，不主动写入 | 「启动即恢复上次值」会在用户无感知的情况下修改系统设置，尤其在开机自启场景下容易造成困惑。只读方案无任何副作用 |
| **自启动机制** | 注册表 `HKCU\...\Run` 键 | 无需管理员权限，实现简单，开关即时生效。备选的任务计划程序方案需一次 UAC 提权且代码复杂度高数倍，其优势（延迟启动、提权运行）本程序均不需要 |
| **窗口行为** | 托盘常驻；关闭与最小化均收进托盘 | FR-2 要求「最小化时快捷键可用」，意味着进程必须保持运行。若关闭按钮直接退出进程，用户极易误操作导致快捷键失效。托盘提供了明确的唤起与退出入口 |
| **自动弹窗的收回时机** | 用户一旦主动介入即转为常驻，不再自动收回 | 无条件倒计时会导致「正拖着滑杆窗口突然消失」。以 `autoShown` 标志区分「快捷键弹出的窗口」与「用户自己打开的窗口」，只有前者才自动收回。判据是所有权而非可见性，逻辑简单且无歧义 |
| **弹窗停留时长的单位** | 毫秒整数，不用秒 | 设置页复用现有的 `ES_NUMBER` 输入框模式，而 `ES_NUMBER` 不接受小数点。要支持「1.5 秒」就得摘掉该样式并自行 `wcstod` 解析、处理非法输入，为一个数字增加的复杂度不划算 |
| **配置文件位置** | `%LOCALAPPDATA%\SdrLuminance\` | 程序同目录在 `Program Files` 下无写入权限 |

## 5. 性能约束与实现手段

| 手段 | 说明 |
|---|---|
| **阻塞式消息循环** | 使用 `GetMessage` 而非 `PeekMessage` 轮询。无消息时线程完全挂起，窗口隐藏后 CPU 占用为 0% |
| **零轮询、零后台线程** | HDR 状态靠 `WM_DISPLAYCHANGE` 事件驱动；热键靠 `WM_HOTKEY` 事件驱动；无任何后台线程 |
| **定时器全部一次性** | 共三个定时器：拖动时的 16 ms 节流合并、快捷键停手后的 400 ms 落盘、自动弹窗的收回计时。三者均为一次性，触发即 `KillTimer`，不存在常驻的周期性回调，故不影响空闲 CPU 占用 |
| **显示配置缓存** | `adapterId` / `targetId` 查询结果缓存，仅在 `WM_DISPLAYCHANGE` 时失效。避免每次调节都执行完整的显示路径枚举（该操作耗时约 0.1–1 ms） |
| **finalValue 写入分级** | 拖动过程传 `0` 仅实时生效不落盘，松手传 `1` 才持久化。消除拖动时的高频系统配置写入 |
| **静态链接 CRT** | `/MT`，产出单文件 exe，无 `vcruntime` 等外部 DLL 依赖 |
| **编译与链接优化** | `/O2 /GL` + `/LTCG /OPT:REF /OPT:ICF`，`WINDOWS` 子系统（无控制台窗口） |
| **原生控件** | 全部 UI 走 `comctl32` 原生控件，不引入任何 UI 框架或图形库 |

**预期指标**：exe < 300 KB，常驻内存 2–4 MB，空闲 CPU 0%。

## 8. 已知限制

### 8.1 独占全屏模式下窗口不可见

**现象**：当前台程序运行于**独占全屏（Exclusive Fullscreen）** 模式时，本工具的调节窗口不会显示在其上方。

**原因**：这是 Windows 桌面窗口管理器（DWM）的硬性行为——独占全屏模式下应用直接接管显示输出，绕过了桌面合成流程，**任何常规窗口都无法覆盖其上**，与本程序的实现方式无关。

**影响范围**：仅影响窗口的可见性。**全局快捷键在独占全屏下仍然完全有效**，只是无法看到窗口界面。

**解决办法**：将游戏的显示模式切换为「无边框窗口化」（Borderless Windowed）。这也是当今绝大多数游戏的默认设置，画质与性能相比独占全屏在现代 Windows 上已无实质差异。

**为何不做技术规避**：唯一的规避方式是向目标进程注入 DLL 并 Hook 其 D3D 交换链绘制 overlay（类似 MSI Afterburner 的做法）。该方式极易被游戏反作弊系统判定为外挂行为导致账号封禁，且带来显著的复杂度与运行时开销，与 FR-4 的性能约束直接冲突。经评估后明确不采用。

### 8.2 依赖非公开 API

写入 SDR 白电平所用的 info type `0xFFFFFFEE` 为 Microsoft 未公开文档化的接口。这意味着未来的 Windows 版本更新**存在改变或移除该接口的可能**。

目前该接口自 Windows 10 1709 起持续可用，且被多个开源项目长期使用验证。程序需对 API 调用失败做健壮处理，失败时给出明确提示而非静默失败或崩溃。

### 8.3 仅支持主显示器

本版本只调节系统主显示器的 SDR 亮度。多显示器环境下的副屏需通过系统设置页手动调节。
